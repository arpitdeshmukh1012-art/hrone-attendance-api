Defects found in the starter `app/main.py` (line numbers refer to the starter). All are fixed in the current `app/main.py`.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |

| 1 | `MongoClient(...)`, l.22 | Client is not `tz_aware`, so PyMongo returns **naive** datetimes; mixing them with IST-aware values raises `TypeError` or silently treats UTC as local time. No server-selection timeout either. | Compare a stored `punch_in` with an aware datetime -> `TypeError: can't compare offset-naive and offset-aware`. | `MongoClient(..., tz_aware=True, serverSelectionTimeoutMS=5000)`; all arithmetic is done on aware UTC/IST datetimes. |

### Looked at and decided **not** a defect
- `load_dotenv()` - its default is `override=False`, so real environment variables already win over `.env`. I made `override=False` explicit for readability.
- `IST = timezone(timedelta(hours=5, minutes=30))` - correct; IST has no DST, so a fixed offset is right (no need for `zoneinfo`).
- `status_code=201` on the two POST create endpoints - matches the contract.
- Storing calendar dates as `"YYYY-MM-DD"` strings and filtering them with `$gte/$lte` - correct, because ISO dates sort lexicographically in date order.
- Synchronous `def` endpoints with PyMongo - FastAPI runs them in a thread pool, and `MongoClient` is thread-safe, so concurrency is handled by the DB constraints, not by the event loop.
